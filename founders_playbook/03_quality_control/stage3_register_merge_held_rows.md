Generated by the orchestrator while applying the four finished Stage-3 dossiers' `## CSV append rows`
into the nine Amazon registers. Rows that do not match the §13 column width were **not** written and are
listed below; nothing is deleted (§14 rule 4), because a held row is a task and a dropped row is a loss.

## Why conflict rows went in under provisional ids

Stage 3 has no `§U` section until assembly, and each dossier invented its own grammar for the conflicts it
found — `ST3_A` used **U.201–U.211** (which also breaks §9.3, since Stage 2 ended at **U.113**), `ST3_B` used
**C-n**, `ST3_C` **U-Cn**, `ST3_D` **U.Dn**. None collide with the 113 registered rows, but four grammars in one
register would make the §U ↔ `conflicts.csv` 1:1 invariant that AUDIT 8 verified unverifiable. So each row was
keyed **P-U.114…P-U.nnn** (provisional), with the dossier's own id preserved inside the `section` column so the
mapping is reversible. At assembly: re-base to **U.114 onward** in this order, write the matching §U blocks,
and the parity check becomes testable again.
